## 1. 如何使用与决定优先级

### 1.1 状态

| 状态 | 含义 |
|---|---|
| 已确认 | 用户已经同意该能力或边界；细节仍可能需要技术设计 |
| 待定 | 已提出但未获得明确选择，或关键行为尚未确定 |
| 暂缓 | 明确不在当前轮次实现；不是永久否决 |
| 不纳入 | 当前 v2 明确不采用 |
| 建议默认 | 为补齐清单提出的默认能力；**未讨论、未批准，不自动进入实现范围** |

清单中的 `K-*`、`P-*` 等是本文功能编号，不是新建的 Epic、Feature 或任务板记录。括号中的 `F01.3h`、`AUTH-08a` 等是对话决定索引，方便续聊追溯，不要求产品实现这些编号。

### 1.2 以最后的明确决定为准

以下变化尤其不能被旧记录覆盖：

1. 首批 Adapter 最终是 **Opengrep、Strix、Trivy**；Trivy 已重新加入。
2. Adapter **预制在 Framework skill 的 `scripts` 中**；Guard 决定参数与调用编排。不是为每条 Policy 预编扫描方案。
3. 首次安装 **知识库与 Preset 为空**，不附带起步知识包。
4. 初装Policies库可以为空；后续已明确：**只使用正式维护的Local或Reference知识，无可用Policies先告知使用者，请Maintainer维护后再使用**。不接受未入库临时文本／文档或工具原生空库检查绕过。
5. 自建命名空间及规则 ID 都带 `@`；不是早期的裸 `CUSTOM-`。
6. 标签是可见的顶层 `tags/`，不是知识目录里的 `.tags/`。
7. 不保留完整本地修订快照；用一份当前内容和可回溯差异日志。来源发布版本仍可并存。
8. Preset 的快照时间固定的是规则清单，**不冻结正文，也不记录正文指纹**。
9. Maintainer 有完整的 secure-code 维护权限；保护边界限制的是 Agent 自行扩大委托，**不是人也无权修改的永久黑名单**。
10. 不对整个 AGENTS 或宿主提示词做幂等锁，只管理显式归属 toolkit 的片段。

## 2. 总体目标与职责

### 2.1 用户目标

- 在旧版基础上构建升级版 secure-code skills。
- 先形成可逐项确认、补充和比较的功能清单，不盲目继承旧实现。
- 在设计与实现过程中内建安全质量；对完成的产物进行有证据的验证。
- 控制 token、工具、运行和维护成本；避免无效建议积累成几千条。
- 允许基于 Lesson 的自主优化，但有明确权限、验证和影响边界。

### 2.3 主要协作链

```text
设计／实现任务
    → Copilot 按需调用 Framework 获取 Policies
    → Copilot 提具体建议
    → 当前执行者落实
    → 独立 Reviewer 核查采纳
    → Copilot 报告＋结构化结果交上游

明确验证请求／已授权验证步骤
    → Guard 确定产物和 Policy 范围
    → Framework 解析有效 Policies
    → Guard 制定检查清单、选择方法与参数
    → 调用 Framework/scripts 内预制 Adapter 或受控辅助检查
    → 复核影响结论的发现
    → Guard 报告＋结构化结果交上游
```

Guard 可独立调用，不强制先有 Copilot 报告。有报告时只参考上下文，不把它当安全通过凭证。

### 3.1 单条 Local 知识

```text
<来源>/<来源版本>/<规则ID>/
├── record.json
├── content.md
├── example.md                 # 可选通用示例
├── example-python.md          # 按需语言示例
├── example-java.md
└── changelog.md
```

- `record.json`：身份、来源位置等元数据；具体 schema 未定。
- `content.md`：当前正式正文，不与示例文件混放。
- `example-{lang}.md`：示例语言，不等于整条规则的适用语言。
- `changelog.md`：正文、元数据和示例的完整前后差异，包括新增、修改、删除。
- Reference 不要求保存完整正文。其记录字段、是否逐条具有 changelog 及转换到 Local 的细则仍需设计，不能照示意图推定所有文件必填。

全部关键条件应同时满足：

1. 真实目标和动作在预授权范围内。
2. 当前 Lesson、正式要求与实际问题证据对应。

- **Maintainer 可明确授权维护这些对象**；“禁止自主放宽”不是剥夺维护者修改权。
- 一般自动优化白名单或维护资格，不默认等同保护控制修改授权。
- 签发、修改授权策略需要真实所有者意图，不由网页、工具、子代理或 Lesson 自证。
- Git 提交、推送和发布不是自主优化的附带权限。
- 精确恢复只限本次自身修改，不能粗暴回滚他人内容；具体恢复实现仍待定。

### 13.4 实现边界

参考 OWASP 最小权限／完整仲裁与 OPA 策略决策、执行分离思想，首版采用轻量规则与实际执行入口校验，不默认部署 OPA 服务。

**没有证据证明所有相关入口受控时，不能宣称实现强制隔离。** 单靠 skill 文案或可绕过脚本只是工作流约束。宿主拦截能力、保护路径、失败行为和实际拒绝写入，都须后续验证。

## 18. 未决项与下一次续聊入口

### 18.1 实现前必须明确的闭环条件

以下是用户要求“按必要性加入”的实施就绪条件，不是新增平台、更多扫描器或本轮已完成验收：

1. **首次成功使用**：确定O-09流程的入口与每步失败提示。只安装接口不表示已安装扫描器；没有默认Preset时仍可依四分支使用已有知识，不增加强制Preset步骤。
2. **知识退出与引用**：停用／删除／重命名由有权维护者决定，先提示影响；定义断链、已知缓存变化和旧报告历史的处理，不自动连带删除。
3. **实际执行边界**：验证角色与动作入口的真实能力。若自主正式写入的全部前提无法可靠满足，则该动作不自动落地、保留候选／请求确认；不是取消已选自主优化目标。宿主提示文件加载验收可继续暂缓，但不能据此省略自动正式写入的必要边界验证。
4. **规则与证据判定**：明确V-24／V-25的冲突口径、最低证据、严重级来源及替代方法条件；不增加复杂百分比评分。
5. **并发与中断一致性**：单条正文、元数据、示例和changelog不会半完成却标成功；输入变化、并发写入和续跑检查点需有明确失效／停止规则，不追求全批次数据库事务。
6. **数据出站**：按E-01／E-02明确授权目的、接收者和数据，实际限制不能只凭`network=true`；不默认把原项目或敏感内容交给外部服务。

### 18.2 后续设计入口

建议按以下顺序继续，避免回头重复已作决定；不是自动任务链或已批准开发计划：

1. **正式Policies与异常格式**：来源只用维护好的知识、轻量可用性及部分可用确认已定；输入schema、Copilot具体空库消息、冲突细则待设计，不重开临时新规则绕过。
2. **主定义与模板正文**：实际字段、文件位置、最小三载体内容；受控部分不锁全文。
3. **授权初始化技术方案**：标准算法、可信文件来源、用途绑定、撤销；不增加真实多用户系统。
4. **Adapter 接口**：Opengrep／Strix／Trivy typed 参数、输出及状态；动态工具规则与临时脚本分开。
5. **执行边界可行性**：Strix 强只读先验证，不可行才副本；SDK／宿主的实际执行入口能力。
6. **默认预算与性能样本**：先明确环境、依赖和费用授权，后实测，不凭宣传定阈值。
7. **建议与 Lesson 状态**：强制评审角色、严重例外、已批准未落地、持久化与终态关系。
8. **旧版其余默认能力**：从 D-01 起逐项取舍；别名、schema、resume等不自动继承。覆盖采用四状态，风险接受只记处置，旧式降级waiver不纳首版。

### 19.1 Copilot、Guard 与指令层的旧版差异
