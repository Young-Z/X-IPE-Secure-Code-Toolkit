如何使用与决定优先级

状态含义

清单中的 K-*、P-* 等是本文功能编号，不是新建的 Epic、Feature 或任务板记录。括号中的 F01.3h、AUTH-08a 等是对话决定索引，方便续聊追溯，不要求产品实现这些编号。

1.2 以最后的明确决定为准

以下变化尤其不能被旧记录覆盖：

  1. 首批 Adapter 最终是 Opengrep、Strix、Trivy；Trivy 已重新加入。
  2. Adapter 预制在 Framework skill 的 scripts 中；Guard 决定参数与调用编排。不是为每条 Policy 预编扫描方案。
  3. 首次安装 知识库与 Preset 为空，不附带起步知识包。
  4. 初装Policies库可以为空；后续已明确：只使用正式维护的Local或Reference知识，无可用Policies先告知使用者，请Maintainer维护后再使用。不接受未入库临时文本／文档或工具原生空库检查绕过。
  5. 自建命名空间及规则 ID 都带 @；不是早期的裸 CUSTOM-。
  6. 标签是可见的顶层 tags/，不是知识目录里的 .tags/。
  7. 不保留完整本地修订快照；用一份当前内容和可回溯差异日志。来源发布版本仍可并存。
  8. Preset 的快照时间固定的是规则清单，不冻结正文，也不记录正文指纹。
  9. Maintainer 有完整的 secure-code 维护权限；保护边界限制的是 Agent 自行扩大委托，不是人也无权修改的永久黑名单。
  10. 不对整个 AGENTS 或宿主提示词做幂等锁，只管理显式归属 toolkit 的片段。

02

总体目标与职责

2.1 用户目标

  • 在旧版基础上构建升级版 secure-code skills。
  • 先形成可逐项确认、补充和比较的功能清单，不盲目继承旧实现。
  • 在设计与实现过程中内建安全质量；对完成的产物进行有证据的验证。
  • 控制 token、工具、运行和维护成本；避免无效建议积累成几千条。
  • 允许基于 Lesson 的自主优化，但有明确权限、验证和影响边界。

    → Guard 报告＋结构化结果交上游

18.1 实现前必须明确的闭环条件
