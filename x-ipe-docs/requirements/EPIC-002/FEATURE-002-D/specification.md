## Overview

FEATURE-002-D delivers the **Trivy Adapter**, the second implementation of the FEATURE-002-B Adapter contract. It gives Guard executable evidence for three kinds of checks that code rules do not cover (user decision 10-22-2026):

- **Vulnerabilities** of declared dependencies (manifests and lockfiles) in `filesystem` mode, and of OS and language packages inside offline container image archives in `image_archive` mode;
- **Misconfigurations** of Dockerfiles, Kubernetes manifests and infrastructure-as-code files (`filesystem` mode);
- **Secrets** hard-coded in files (`filesystem` mode).

"Container" means configuration files scanned for misconfigurations **and** image archives produced by `docker save` (`.tar`) that are verification targets, scanned for vulnerabilities only; there is no Docker daemon, no registry and no live image (user decisions). License scanning and compose-file misconfiguration analysis are out of scope.

- **Guard decides, the Adapter executes.** As in FEATURE-002-B, Guard chooses whether Trivy is the cheapest sufficient method for a planned check and which scanners, targets, mode and time limit to use, and records why. The script validates these named parameters, runs the tool inside the open Guard verification on private snapshots, accounts for every object file, normalizes the output into per-check `runtime` evidence and findings, and never decides a verdict.
- **Only the authentic, known binary runs, on Linux only.** A Maintainer registers the `trivy` binary; registration and every run compare its SHA-256 with the toolkit's table of official digests for Trivy **v0.76.1** before anything is executed. Execution is supported on Linux x86-64 and Linux arm64 only in this version; macOS and Windows are refused with an honest gap (user decision).
- **Scans are offline; the databases are provisioned separately and only with permission.** A scan never updates anything and needs no network. The vulnerability database, the Java database and the checks bundle reach the project's private cache only through a Maintainer provisioning command that names an open verification holding a FEATURE-002-C **tool/vulnerability-database update** (`tool_update`) grant whose scope covers the exact repository of every component provisioned; the download is charged to that verification's budget and shown in its report (user decision H1). The repository is fixed by configuration of the launched tool; network access is not OS-enforced (stated limit). Every run reports the state of each component; a missing component is a reported gap, never a silent download. No staleness threshold is invented: the age is reported and Guard decides whether it is sufficient (user decision).
- **Honest results.** Tool errors, a missing database or checks bundle, unrecognized, unsupported or skipped files, skipped packages, timeouts and unparseable output make the affected check's evidence a failed method; a clean exit with zero findings is evidence, never a pass. Secret values are never stored in plaintext (user decision).
- **Validated before built.** A tool-level validation of Trivy v0.76.1 on both MVP samples, self-authored fixtures and local image archives was performed during refinement ([tool validation](x-ipe-docs/requirements/EPIC-002/FEATURE-002-D/tool-validation/README.md)); formal evaluation (AC-28) belongs to FEATURE-003-C.

This feature reuses FEATURE-002-B (contract, registration, staging, process control, evidence/finding provenance) and FEATURE-002-C (budget, cancellation, egress grants and coverage, the Adapter network-need check) without changing their acceptance criteria. It needs one additive extension of the shared FEATURE-002-B digest-table contract (C-library-independent Linux entries, AC-002D-01f) and changes one reported fact of FEATURE-002-B: `status` now reports Trivy as provided (AC-002B-06b keeps applying to Strix).

## User Stories

- **US-01:** As a Developer, I want Guard to check my declared dependencies, container image archives, configuration files and files for secrets with Trivy and record the real output as runtime evidence, so that these checks can be met instead of staying unconfirmed.
- **US-02:** As a Guard agent, I want to pass only named, validated parameters (scanners, targets, mode, time limit) through the shared Adapter contract, so that I decide the scan strategy without writing command lines and without a Policy-to-scanner mapping.
- **US-03:** As a Maintainer, I want only the authentic released Trivy binary to be registered and run on a supported platform, so that a swapped or unknown tool is never executed.
- **US-04:** As an Owner, I want the databases to be downloaded only by an explicit Maintainer action under a purpose-specific update grant naming the exact repositories, and scans to stay offline, so that no data leaves and nothing is downloaded behind my back.
- **US-05:** As a Developer, I want every result to state the state and age of the databases it was based on, and a missing component to be reported as a gap, so that I can judge whether "no known vulnerability" means anything.
- **US-06:** As a Developer, I want skipped, unrecognized and unsupported files, skipped packages, tool failures and timeouts reported per check, so that a clean exit or zero findings is never mistaken for a pass.
- **US-07:** As a Developer, I want secrets found by the tool reported without their values, so that the evidence and reports do not spread the credentials they warn about.
- **US-08:** As a Developer, I want the original project protected from the tool, so that verification never changes my files.
- **US-09:** As a Maintainer, I want a recorded tool-level validation before the full Adapter, so that known tool behaviour and issues are evidence, not assumptions.

## Acceptance Criteria

Breakdown ACs: AC-002D-01 (no database download without a "tool/vulnerability-DB update" authorization; database state or gap reported honestly) → AC-002D-02a…02h, 04c, 05i; AC-002D-02 (tool-level validation on the MVP samples precedes the full Adapter; observed results and known issues recorded; formal evaluation AC-28 in FEATURE-003-C) → AC-002D-07a, 07b. EPIC-001 AC-24 (Trivy part) → 01*, 03*, 04*, 05*. "Parameters, targets and mode" (FR-16) for Trivy are the scanners, the scan targets and the scan mode `filesystem` or `image_archive`; "budget" is the per-run time limit within the FEATURE-002-C shared budget. Commands are named here for readability; final names and request schemas are fixed in technical design.

**Two-phase failure semantics (as implemented by FEATURE-002-B):** a request that is malformed or violates a parameter rule (AC-002D-03) is **refused** — no attempt is registered and no evidence is recorded. Only an **accepted** request registers its tool attempt; if its pre-check then fails (platform, registration, binary digest, database component, staging), failed `runtime` evidence is recorded for the affected requested checks (AC-002D-01c, 01d, 02e, 03f). Provisioning refusals decided after the named verification is accepted are recorded only as refused egress declarations (AC-002D-02a), never as attempts or evidence.

## Functional Requirements

- **FR-002D-1 Trivy on the Adapter contract.** Trivy is a provided Adapter of the FEATURE-002-B contract: official-digest table entries for v0.76.1 (Linux x86-64, Linux arm64; C-library-independent, AC-002D-01f), supported execution platforms (Linux only), named parameter schema, pre-check, protected execution with a total time limit, coverage accounting and normalization into per-check status, findings and evidence provenance. Its scan network need is "none"; provisioning needs purpose `tool_update` with data `metadata` and a scope per component repository (FEATURE-002-C, unchanged contract).
- **FR-002D-2 Registration (Maintainer).** Input: tool `trivy`, binary path. Process: Maintainer authorization (FEATURE-001-A); regular file, no symbolic link; digest; lookup in the official-digest table **without executing the binary**; supported Linux platform and architecture. Output: the existing machine-local registration record (path, digest, version, `asset`, platform, validation state, time). Re-registration replaces it explicitly.
- **FR-002D-3 Database provisioning (Maintainer).** Input: verification id, components (any of vulnerability database, Java database, checks bundle), time limit. Process: Maintainer authorization; supported platform; binary pre-check; for each component a `tool_update` grant on that open verification whose recipient is the component's repository origin, data includes `metadata` and scope covers the component's exact repository path and tag, plus one covering `tool_update` grant (data `metadata`) per further host in the repository's known-host list for v0.76.1 (`ghcr.io` → `pkg-containers.githubusercontent.com`) — all checked with the FEATURE-002-C coverage rules, unchanged; an uncovered known host or a repository/tool version without a validated known-host list → refused before launch with a `used: false` declaration naming it; budget and cancellation of that verification; one operation per component, running the binary snapshot configured with exactly that one repository, fallback repository disabled, version check and telemetry disabled, no project input; replace the component in the project's private cache (per project, under `.x-ipe/private/secure-code/`) only when its download completed and is readable, recording the digests of its files. Refusals after the named verification is accepted are recorded as refused `used: false` declarations without attempt, budget charge or execution (AC-002D-02a). Output: per-component result with the repository, tag and digest/metadata actually used (FR-002D-7), egress record listing every known host of each operation, budget consumption, report entry. The known-host list and the single configured repository are configuration-level expectations of the launched tool, not network enforcement; contacts outside the list cannot be detected at runtime.
- **FR-002D-3a Component removal (Maintainer).** Input: one component or all. Process: Maintainer authorization; refused while a scan or provisioning of the project is in progress; remove the named components from the project's private cache only. Output: removed components and bytes freed; `status` then reports them `missing`. No network, no grant, no tool execution, no project file touched.
- **FR-002D-4 Pre-check (accepted requests).** Before executing: platform supported; tool registered; binary snapshot digest = registration = table; required components present and readable for the requested scanners and mode; targets stageable within the evidence bounds. Failure → no execution; failed method with reason for every requested check (component failures: only the checks needing it); next step. Requests failing FR-002D-5 are refused before this phase (no attempt, no evidence).
- **FR-002D-5 Run request.** Verification id; total time limit (required, ≤ documented maximum, capped by the remaining budget); per check: scanners ⊆ {`vuln`, `misconfig`, `secret`} (non-empty), mode `filesystem` | `image_archive` (`image_archive` only with exactly `vuln` and only `docker save` `.tar` targets), scan targets covering the check's full object, optional configuration-type overrides for target files (`misconfig` types supported by the verified version). Only for an open verification with a plan and checks declaring a selected or activated `trivy` runtime method. Violations are refused (no attempt, no evidence).
- **FR-002D-6 Protected offline execution.** Snapshot (no symbolic links followed) the binary and the requested targets (including image archives) into private staging; require binary digest = registration = table and staged target digests = digests recorded at open; run the binary snapshot without a shell on staged paths only, with disposable working folder, home, temporary folder and scan cache, a minimal environment, every update and remote lookup disabled, version check and telemetry disabled, and project configuration, ignore and secret-configuration files disabled; read the provisioned components in place, then re-hash every used component against its provisioning digests (a change fails the affected checks and marks the component invalid until re-provisioned); stop the tool and its children at the effective time limit (the tool's own deadline is never shorter); remove staging and disposable locations; confirm original targets and context unchanged.
- **FR-002D-7 Component state.** Per component: present / missing / unreadable (including invalid after a detected change, with reason), and on-disk size. Vulnerability database and Java database: `Version`, `UpdatedAt`, `NextUpdate`, `DownloadedAt`, age (time of reporting minus `UpdatedAt`). Checks bundle: `MajorVersion`, `Digest`, `DownloadedAt`, source repository (no age). Reported in run evidence, provisioning results and `status`. No threshold; Guard judges sufficiency.
- **FR-002D-8 Accounting and normalization.** Statuses as in FEATURE-002-B: `completed`, `completed_with_errors`, `failed`, `timed_out`, `precheck_failed`. Per check and scanner: object files analysed / skipped (with the tool's reason) / unrecognized / unsupported (compose for `misconfig`) / unaccounted; packages skipped by the tool; image OS detection; checks source (provisioned bundle, or embedded fallback = gap). Evidence `ok` only when everything is accounted for and nothing failed. Results → findings with tool provenance and the documented severity mapping (`unknown` fallback), attributed per check. Secret values never stored (FR-002D-9). All persisted text masked.
- **FR-002D-9 Secret handling.** A secret result keeps rule id, category, tool severity, location and line range, and a masked or non-reversible representation of the value; plaintext and the tool's context lines are dropped before anything is persisted; the stored masked tool output contains no secret context lines.
- **FR-002D-10 Method choice, status and skill.** Method choice and changes as in FR-002B-7; `status` tools section per FR-002D-7 and AC-002D-08a; Guard skill and references updated per AC-002D-06d.

## Non-Functional Requirements

- **NFR-002D-1 Safety.** No shell; no download, install or upgrade by the toolkit except a Maintainer provisioning under covering `tool_update` grants; binary authenticity checked by digest on the private snapshot that is executed; the provisioned components are read in place by that binary, which is trusted not to write to them, and any change is detected by re-hashing after every scan (detection, not prevention); scans pass only staged paths and run with every network-using feature disabled. Filesystem and network access by the launched tool are not OS-enforced (no OS isolation, FEATURE-002-B/002-C limit): during provisioning the configured single repository, the disabled fallback and the known-host list per repository (pinned to v0.76.1 from the tool-level validation: `mirror.gcr.io` → `mirror.gcr.io:443`; `ghcr.io` → `ghcr.io:443` and its blob host `pkg-containers.githubusercontent.com:443`) are configuration-level expectations; every known host must be covered by a `tool_update` grant and is listed in the egress record, but individual requests of the launched tool (registry endpoints such as `/v2/`, redirects) are not gated, and contacts outside the known list cannot be detected at runtime — a stated limit, never presented as enforcement.
- **NFR-002D-2 Privacy.** No secret plaintext in any stored or reported field (AC-002D-05c), verified with a self-authored fake credential; all other stored text masked (FEATURE-002-A); masking limits of NFR-002A-2 restated in the report.
- **NFR-002D-3 Determinism of normalization.** The same tool output, inputs and component state always normalize to the same findings, accounting and statuses.
- **NFR-002D-4 Bounded resources.** Every scan and provisioning operation has a total time limit within the verification's budget; image archives are limited to 8 GiB each; other staged copies and stored output follow the existing FEATURE-002-A/002-B bounds; re-hashing the components after each scan adds time proportional to their size (measured in the tool-level validation); the provisioned cache lives per project and its per-component on-disk size is reported in `status` (observed ≈3.2 GB on disk with the Java database, ≈1.07 GiB downloaded).
- **NFR-002D-5 Portability.** Trivy registration, provisioning and execution on Linux x86-64 and Linux arm64 only in this version (user decision 10-22-2026); on macOS and Windows they are refused with a clear gap while `status` works. Tool-level validated: Linux arm64 (container) only; the Linux x86-64 official digest is known but not executed. The Linux binaries are statically linked (observed), hence C-library-independent entries (AC-002D-01f).

## UI/UX Requirements

No graphical UI. Extended `secure-code` commands (names finalized in technical design): `tools register --tool trivy` (Maintainer), a Maintainer provisioning command for the Trivy components bound to an open verification, a Maintainer removal command for provisioned components (one or all), the existing Guard tool-run command with `adapter: trivy`, and `status` (with each component's on-disk size). Every command returns the toolkit result envelope (text and `--json`) with one next step per refusal. The Guard report shows each Trivy run (tool version, platform validation state, scanners, mode, status, component state, per-check accounting with gaps, errors) and each provisioning operation (component, repository and tag, metadata, grant, budget consumption, outcome, configuration-level limit), the method choice per check and any switch or supplement with reasons.

## Business Rules

- **BR-01:** Framework scripts hold the Adapter; Guard decides whether and how to call it; no Policy→scanner or Policy→check-id mapping is pre-maintained (A-01…A-04, O-06).
- **BR-02:** Only named parameters; never a shell string or arbitrary tool option (A-03). Invalid requests are refused without an attempt or evidence; only accepted requests that fail their pre-check record failed evidence.
- **BR-03:** Only a binary matching an official v0.76.1 release digest for a supported Linux platform is registered or run, checked before execution; failures are reported gaps, never a download, upgrade or relaxation; a passed pre-check is not a security pass (A-08, A-09; user decision).
- **BR-04:** Scans are always offline and never update anything; components reach the cache only through Maintainer provisioning naming an open verification with a `tool_update` grant whose scope covers each component's exact repository path and tag; the download is charged to that verification's budget and shown in its report (E-01; user decisions 3, H1). A `tool_update` grant never authorizes sending project content (AC-29).
- **BR-05:** The toolkit reports component state and database age and never applies an invented staleness threshold; Guard judges and records sufficiency (user decision).
- **BR-06:** The tool works on disposable snapshots of the targets; the original project is never handed to it. The provisioned components are read in place and re-hashed after every scan; a detected change invalidates the component and the affected evidence (FR-17 principle; user decisions, D-e).
- **BR-07:** Anything not analysed by the tool — skipped, unrecognized, unsupported (compose for `misconfig`) or unmentioned files, skipped packages, undetected image OS, embedded-checks fallback — and any error, timeout or unparseable output makes the affected check's tool evidence a failed method; FEATURE-002-A decides what that means for the check (required vs auxiliary) (user decisions H2, H4).
- **BR-08:** Secret plaintext is never stored or reported; only rule, location and a masked or non-reversible value (user decision).
- **BR-09:** Tool findings are findings like any other: reviewed when verdict-affecting or of unknown severity, never deleted (FEATURE-002-A BR-07). All severities are recorded; no severity filtering.
- **BR-10:** Only a Maintainer registers the tool or provisions its components; neither is consent to run against new targets, with more permissions or with network access during scans (A-06).
- **BR-11:** Cheapest sufficient method first; the choice and any switch or supplement are recorded with reasons; Trivy is never run by default (A-05…A-07).
- **BR-12:** `image_archive` mode is limited to `vuln` on `docker save` archives in this version; secrets and misconfigurations are checked on files in `filesystem` mode (user decision H3).
- **BR-13:** Provisioned components live per project in its private folder and are removed only by an explicit Maintainer removal command, never while a scan or provisioning of the project is in progress (D-a). Image archives are accepted only as explicitly declared `docker save` file targets of at most 8 GiB with a valid structure (D-b, D-c, D-d).

## Edge Cases & Constraints

Observed tool facts are from the [tool validation](x-ipe-docs/requirements/EPIC-002/FEATURE-002-D/tool-validation/README.md) (Trivy v0.76.1, Linux arm64).

| Scenario | Expected behaviour |
|---|---|
| Malformed request, unknown field, `license` scanner, severity filter, `secret`/`misconfig` in `image_archive` mode, registry image name | Refused; no attempt, no evidence, nothing executed (AC-002D-03f) |
| Trivy not registered, or binary replaced after registration | Accepted request's pre-check fails before execution; failed method per check; next step: Maintainer registration |
| Host is macOS or Windows | Registration and provisioning refused; run pre-check fails with the platform gap; nothing executed; `status` shows "not supported on this platform in this version" |
| Linux binary of another version, a release archive or another-architecture build | Registration refused without executing it |
| No vulnerability database provisioned | Vulnerability checks: failed method "vulnerability database missing" + provisioning next step (the tool itself exits 1 "cannot skip DB update on the first run" — observed); secret checks of the same request still run |
| Corrupted or unreadable vulnerability database | Failed method for vulnerability checks with the tool's message (observed exit 1 "invalid database"); next step: re-provision |
| Image archive containing Java archives and no Java database | Vulnerability check of that image: failed method naming the Java database (the tool aborts the whole image scan — observed) |
| No checks bundle provisioned, or the tool falls back to embedded checks | `misconfig` checks: failed method "checks bundle missing / embedded fallback" with next step "provision the checks bundle" (observed: tool logs ERROR "Falling back to embedded checks", exit 0, 563 embedded vs 580 downloaded checks) — the fallback is never complete evidence (user decision H4) |
| Database far past `NextUpdate` | Scan runs offline on it without warning from the tool (observed); the evidence reports the age; Guard decides sufficiency |
| Provisioning without grant, with a grant for another origin, purpose or data, with a scope not covering a component's repository path and tag, or for a finished/cancelled verification | Refused before execution for the uncovered components; nothing downloaded |
| Checks-bundle download fails (repository unreachable or refused) | The tool exits 0 with ERROR "Falling back to embedded checks" and writes nothing (observed); the operation is a failure because the provisioned `policy/` subtree and metadata are absent — exit 0 is never taken as success |
| `ghcr.io` operation | The tool also contacts its blob host `pkg-containers.githubusercontent.com` (observed); this host is in the known-host list for `ghcr.io` (v0.76.1) and needs its own covering `tool_update` grant besides the repository grant; without it the operation is refused before launch with a `used: false` declaration naming the host; when executed, the egress record lists both hosts (DAO-001 under delegation, AC-002D-02b) |
| Same component from `mirror.gcr.io` and `ghcr.io` | Not interchangeable (observed: different checks-bundle digests at the same moment); the provisioned repository, tag and digest/metadata are recorded per component, and reports and scan evidence cite the repository and digest actually used, never implying equivalence between registries |
| Trivy version other than v0.76.1, or a repository without a known-host list | Provisioning refused before launch (`used: false` declaration naming the missing list); a new version needs tool-level re-validation before its known-host list is trusted |
| Default repository unreachable during provisioning | The operation fails and is reported; the tool's fallback repository is not used automatically; the Maintainer may run a separate operation for the `ghcr.io` repository under its own covering grant |
| Provisioning interrupted, cancelled, timed out or failing on the network | Previous complete component state kept (or "missing"); outcome reported; partial download never used; time charged to the named verification |
| Provisioning while another verification scans | The scan uses one complete component state and reports the state it used |
| `pom.xml` whose versions come from a parent POM | Offline the tool cannot resolve them: packages without a version are skipped (observed 18 on WebGoat, reported only in debug output) and transitive dependencies are not found; skipped packages are named gaps; the evidence states that transitive dependencies are not analysed offline |
| Files the secret scanner skips by its built-in rules (test folders, `examples/`, `node_modules/`, `.git/`, Markdown, binaries) | Listed as not scanned; that secret check's tool evidence is a failed method; Guard may narrow the object or add another method (observed: WebGoat 985 of 1,243 files scanned) |
| Configuration file with a non-standard name (e.g. `Dockerfile_desktop`) | Not recognized by default (observed) → gap; Guard may pass a configuration-type override, which makes the tool analyse it (observed) |
| docker-compose file in a `misconfig` check | Gap "configuration type not supported by Trivy v0.76.1" (observed: not analysed, no message) → failed method, next step: another method such as Guard semantic review (user decision H2) |
| docker-compose file in a `secret` check | Treated as an ordinary text file by the secret scanner (expected; not validated specifically for compose files) |
| Java archive given in `filesystem` mode | Not analysed by the tool (observed) → gap; Java archives are analysed inside image archives |
| Image archive without a detectable OS (e.g. `hello-world`) | No result from the tool (observed); vulnerability coverage gap "OS not detected" |
| `image_archive` target that is not a `docker save` archive (folder, pure OCI layout without `docker save` `manifest.json`, other file) | Refused at validation (AC-002D-03c, 03h); a file the tool still cannot open as an image fails with the tool's message (observed exit 1) → failed method |
| `docker save` archive from Docker ≥ 25 (also contains `oci-layout`, `index.json`, `blobs/`) | Accepted; its `docker save` `manifest.json` is authoritative (the validation archives were produced this way by Docker 29.7.2) |
| Archive with a link, device or duplicate member, an absolute or `..` member name, or a `Config`/`Layers` reference to a missing member | Refused naming the violation (AC-002D-03h) |
| Image archive larger than 8 GiB | Refused with its size and the maximum (AC-002D-03g) |
| `.tar` file inside a declared folder target | Not an image archive; for `filesystem` scanners an ordinary file (AC-002D-03i) |
| A provisioned component changes during or after a scan | Detected by the post-scan re-hash: affected checks failed, component `unreadable` with reason until re-provisioned (AC-002D-02g) |
| Component removal requested while a scan or provisioning runs | Refused; nothing removed (AC-002D-02h) |
| Provisioning refused for a missing grant after the verification was accepted | Refused `used: false` declaration recorded in that verification's egress record; no attempt, no budget, no execution (AC-002D-02a) |
| Very large image archive or target | Image archives above 8 GiB refused at validation; other targets bounded by the existing staging limits → failed with the bound named; time limit stops the run → `timed_out` |
| Vulnerability without details (`UNKNOWN` severity) | Finding with Guard severity `unknown` (needs review); the tool's warning is recorded |
| Secret found | Stored with rule, location and masked value only; context lines dropped (the tool masks only what its rules detect — observed) |
| Project contains `trivy.yaml`, `.trivyignore` or `trivy-secret.yaml` | Never loaded (they would otherwise be read from the working directory — observed) |
| Tool's own internal deadline reached | Treated as `timed_out` (observed exit 1 "context deadline exceeded", no JSON) |
| Verification already concluded or cancelled | Refused (`RUN_FINISHED` / cancelled), as for FEATURE-002-B/C |

## Out of Scope

- License scanning; SBOM generation or SBOM scanning (not in the sources for this feature); compliance reports, VEX, ignore files and policies, severity filters, `--ignore-unfixed`.
- Misconfiguration analysis of docker-compose files by Trivy in this version (user decision H2; such checks need another method).
- Secret and misconfiguration scanning inside image archives (user decision H3); pure OCI layout archives (without a `docker save` `manifest.json`) and any image input other than an explicitly declared `docker save` `.tar` file up to 8 GiB (R3, D-b, D-c, D-d).
- Live or registry images, Docker/containerd/Podman daemons, registry authentication, Kubernetes cluster, VM, root-filesystem and remote repository scans.
- Trivy execution on macOS and Windows in this version; Linux architectures other than x86-64 and arm64.
- Repositories other than the tool's official repositories; automatic fallback between repositories; private registries; scheduled or automatic database refresh; a fixed staleness threshold; using the embedded checks as complete evidence.
- Custom Rego checks, custom secret rules or disabling the tool's built-in secret skip rules (not validated; runtime rule generation A-11 deferred).
- Signature (sigstore/cosign) verification (official release digests and the checksums file are used instead); custom or self-built binaries.
- Standing (per-project) egress grants and any FEATURE-002-C contract change (user decision H1); OS-level network or process isolation.
- Formal performance/effectiveness evaluation and delivery bar (AC-28, FEATURE-003-C); detection-quality claims.

## Technical Considerations

- Observed tool facts to respect (v0.76.1, see the tool validation): scan flags `--skip-db-update --skip-java-db-update --skip-check-update --offline-scan --skip-version-check --disable-telemetry` gave zero outbound attempts; without them the tool contacts `mirror.gcr.io`, `check.trivy.dev` or Maven Central, often silently; repositories are selectable per component (`--db-repository`, `--java-db-repository`, `--checks-bundle-repository`) and the database options accept a priority list with a `ghcr.io` fallback by default, so one explicit repository must be configured per operation; exit 0 with or without findings, 1 for every fatal error, `--exit-code` overloads it; JSON has no per-file coverage for secrets — scanned files appear only in debug lines ("Using streaming scanner"), skipped packages only in debug lines; recognized manifests and configuration files appear as results even without findings (`MisconfSummary`); the embedded-checks fallback is visible only as an ERROR log line with exit 0; image scans need a writable scan cache unless the memory backend is used; `trivy --version --format json` reports component metadata; component metadata is in `metadata.json` files readable without executing the tool; default tool deadline 5 minutes.
- WHAT-level requirements for the shared contract (FEATURE-002-B): C-library-independent Linux entries (AC-002D-01f); `asset` names the source archive; per-Adapter supported execution platforms. Grant checks use the FEATURE-002-C coverage function with each component's repository URL prefix as scope (FEATURE-002-C URL rules); how the provisioning attempt is registered and charged is decided in design within the FEATURE-002-C acceptance criteria.
- Decided in technical design, with version-specific tests: exact command options, whether runs are split per check and per scanner to isolate failures, parsing of version-specific debug output (an unrecognized log format means accounting fails → failed method), detection of the embedded-checks fallback, the canonical URL form of repository scopes, the per-project cache layout under `.x-ipe/private/secure-code/`, how provisioning replaces components atomically and records file digests, how the post-scan re-hash and the invalid mark are implemented (the validation measured the re-hash time of each component), how removal detects a scan or provisioning in progress, how the archive structure is parsed safely, the representation used for secret values (if a hash is used it must not allow recovering low-entropy values), the configuration-type list, severity mapping table, maximum time limits for scans and provisioning, and command names.
- Validated provisioning argv (v0.76.1, one repository each, fallback list replaced): vulnerability database `image --download-db-only --db-repository <repo:2> --skip-version-check --disable-telemetry --no-progress --cache-dir <dir>`; Java database `image --download-java-db-only --java-db-repository <repo:1> …` (same flags); checks bundle (no download-only option) `fs --scanners misconfig --checks-bundle-repository <repo:2> --skip-db-update --skip-java-db-update --offline-scan --skip-version-check --disable-telemetry --no-progress --format json --cache-dir <dir> <empty folder>` (or `config` without `--no-progress`). Each wrote only its own subtree (`db/`, `java-db/`, `policy/`).
- Re-hash cost measured for D-e: ≈0.5 s per database (≈1.6 GB each, ≈3 GB/s, warm page cache) and ≈0.01 s for the checks bundle; cold-cache cost not measured.
- The provisioned cache is large (≈1.6 GB vulnerability database, ≈1.6 GB Java database on disk; Java database download ≈941 MiB, ≈6.5 minutes in validation); provisioning time counts toward the named verification's budget.
