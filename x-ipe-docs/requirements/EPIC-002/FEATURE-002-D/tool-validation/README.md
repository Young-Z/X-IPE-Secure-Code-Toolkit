## Known Issues and Consequences for the Adapter

1. **Network by default.** Without the skip flags the tool updates its DB, Java DB and checks from `mirror.gcr.io` (documented fallback `ghcr.io`), contacts `check.trivy.dev` (version check/telemetry, default on) and, for `pom.xml` without `--offline-scan`, Maven Central with dependency coordinates. Failed network calls are often silent (exit 0, same results). → Every scan must pass the full offline flag set; DB/checks updates happen only in a separate provisioning step under a `tool_update` grant (FEATURE-002-C), with version check and telemetry disabled there too.
2. **DB state is not judged by the tool.** With updates skipped, a DB with a 2019 `UpdatedAt` is used silently. A missing or corrupted DB is fatal (exit 1) for vulnerability scanning only; secret scanning needs no DB; Java archives in image archives need the Java DB (the whole image scan fails without it). → The Adapter reports each component's metadata itself (databases: `Version`, `UpdatedAt`, `NextUpdate`, `DownloadedAt` and age; checks bundle: `MajorVersion`, `Digest`, `DownloadedAt`) and fails only the checks that need the missing component; Guard judges sufficiency.
3. **Coverage is not in the JSON.** Recognized manifests and configuration files appear as results even without findings, but secret-scanned files appear only when they contain a finding. The secret scanner silently skips test folders, `examples/`, `node_modules/`, `.git/`, Markdown and binary files; only debug lines name the scanned files. Configuration files are recognized by name (`Dockerfile_desktop` missed by default; recognized with a file pattern); docker-compose files are not analysed at all; Java archives are not analysed in filesystem mode; an image without a detectable OS yields no result. → Per check, every object file must be accounted for from the tool's own statements (results plus version-specific debug lines); anything else is a named gap and makes that check's evidence a failed method. Compose files in a misconfiguration check get the explicit gap "configuration type not supported by Trivy v0.76.1" (human decision H2); they remain ordinary text files for the secret scanner (expected, not validated specifically for compose).
4. **Offline Maven analysis is partial.** Versions managed by an unreachable parent POM are not resolved: 18 WebGoat packages were not checked and transitive dependencies are not found, reported only in debug lines and one generic WARN. → Skipped packages are coverage gaps; the evidence states that transitive dependencies not listed in the manifest are not analysed offline.
5. **Exit status.** 0 with or without findings; 1 for every fatal error (missing target, unknown flag or scanner value, missing/corrupted DB, missing Java DB, non-image input, tool deadline); stdout empty on fatal errors. `--exit-code` overloads the exit status. ERROR/WARN lines can accompany exit 0 (embedded-checks fallback, undetermined versions, missing vulnerability details). → Never use `--exit-code`; exit ≠ 0 or unparseable output is a failed run; degrading log lines are recorded with the evidence. The embedded-checks fallback (563 embedded vs 580 provisioned checks) is a coverage gap, never complete misconfiguration evidence (human decision H4).
6. **Own deadline.** The tool stops itself after 5 minutes by default with exit 1 and no JSON. → The tool's deadline must not be shorter than the Adapter's effective time limit, and a deadline expiry is reported as timed out, not as a clean run.
7. **Secrets.** The tool masks the detected value in `Match` and `Code`, but `Code` carries surrounding lines in clear text, and only values its rules detect are masked. → Store only rule, category, severity, location and a masked or hashed value; never the tool's context lines; mask every stored field with the FEATURE-002-A patterns.
8. **Project files can change the scan.** `trivy.yaml`, `.trivyignore` and `trivy-secret.yaml` in the working directory are loaded by default (suppressing findings or changing rules). → Disable all three and run in a disposable working folder.
9. **Cache writes.** Image scans with the default scan cache create `fanal/fanal.db` in the cache directory (fatal on a read-only cache); with the memory backend nothing is written; filesystem scans never wrote. → Scans must not modify the provisioned DB cache; any scan cache is disposable.
10. **Image archives.** Secret and misconfiguration scanners also ran on the `redis:6-alpine` archive (no config file or secret found), but per human decision H3 this version allows only `vuln` in `image_archive` mode and only `docker save` `.tar` archives (the tool also accepts OCI layouts — not used); secrets and misconfigurations are checked on files.
11. **Severity.** Tool severities `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, `UNKNOWN` (observed for rejected/undetailed CVEs); `--severity` drops lower results. → No severity filter in requests; `UNKNOWN` maps to Guard `unknown`.
12. **Size and time.** The provisioned cache is ≈3.2 GB on disk (≈1.07 GiB downloaded); the Java DB alone took ≈6.5 minutes here (384–388 s). Scans themselves took ≤0.61 s and ≤331 MB RSS on these samples.
13. **Repository selection.** Each component's repository is a tool option (`--db-repository`, `--java-db-repository`, `--checks-bundle-repository`); the database options default to a priority list with a `ghcr.io` fallback. → Provisioning configures exactly one repository per operation; this is a configuration-level constraint of the launched tool, not network enforcement (the tool also contacts the registry's `/v2/` endpoint, seen in an error message).
14. **Not exercised:** the linux/x86-64 binary (hash only), macOS and Windows (out of scope for execution in this version), the conditions under which the default repository list falls back to `ghcr.io` (Known Issue 18), cold-cache re-hash time, signature verification, real registry or daemon images (out of scope), detection quality (formal evaluation is FEATURE-003-C, AC-28).

### Provisioning (TASK-056 extension)

15. **No checks-bundle download-only option.** A misconfiguration scan of an empty folder (`fs` as above, or `config` without `--no-progress`) fetches only the bundle into `policy/`; nothing else is written. → Provisioning uses that argv and verifies the resulting `policy/` subtree itself.
16. **A failed checks-bundle download exits 0.** With the repository refused, the tool logs ERROR "Falling back to embedded checks", exits 0 and writes nothing. → Exit 0 is not success for checks-bundle provisioning; the `policy/metadata.json` and `policy/content/` subtree and the absence of the fallback line must be verified.
17. **Second origin behind `ghcr.io`.** `ghcr.io` serves blobs from `pkg-containers.githubusercontent.com:443`, so a `ghcr.io` operation contacts two origins; `mirror.gcr.io` operations contacted only `mirror.gcr.io:443`. → A grant naming the `ghcr.io` origin does not name the blob host; the launched tool's redirects are not gated (stated limit).
18. **Fallback and repository differences.** With a single repository configured, a refused mirror led to failure without any `ghcr.io` attempt (fallback disabled as intended). The default two-entry list did not fall back either when the mirror was refused at the proxy, so the tool's fallback conditions remain undetermined; configuring one repository is the only reliable control. The two repositories served different checks-bundle digests at the same moment (`b591e919…` vs `b0e12d00…`), so the provisioned source repository and digest must be recorded per component. A superseded first attempt (driver `cbeba0e9…`, whose proxy closed tunnels idle for 60 s) saw a transient GitHub release download failure (SSL EOF) and two `ghcr.io` database downloads aborted with stream errors; after removing the idle timeout all operations succeeded — large `ghcr.io` downloads may be sensitive to connection interruptions.
19. **Re-hash cost.** Re-hashing both databases took ≈1 s (≈3 GB/s, warm page cache) and the checks bundle ≈0.01 s; cold-cache cost was not measured.
