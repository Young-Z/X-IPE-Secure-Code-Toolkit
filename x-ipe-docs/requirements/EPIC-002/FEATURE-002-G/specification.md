## Overview

FEATURE-002-G lets a Developer ask, explicitly, "what changed between these two Guard verifications?" The user names exactly two concluded Guard reports of one project. The deterministic `secure-code` script reads only those two structured results (and their Markdown reports, for the consistency check), matches findings across the runs by a defined identity, and classifies every finding as **new**, **still present**, **not observed this time** or **not comparable**. It never re-scans, never runs a tool or model, never uses the network and never writes into the two runs.

The central rule is **not observed ≠ fixed**. A finding that is absent from the later run is "not observed this time" only when the later run really looked at the same place, under the same adopted Policy, with the same kind of method and the same tool and tool data; otherwise it is "not comparable" with the reasons. A new finding is "new" only under the same conditions. A finding observed in both runs under the stated identity rule is "still present", with every Policy, tool and tool-data difference noted (DAO-010 OQ-03); it is never called "the same issue confirmed". Nothing is ever called fixed, resolved or improved, and no trend score or percentage is produced.

Inputs are checked before use: each named report must be exactly `<verification-id>.json` or `.md` directly in the project's `reports/guard/` folder, reached without symbolic links; the structured result must pass strict validation of every field the comparison consumes; and the complete Markdown report is compared with a canonical rendering of the structured result. Any inconsistency is stated first and the run is marked "input integrity unresolved"; the structured result is used only after it passes strict validation, and nothing is ever repaired or written in a compared run.

Comparison identity is honest about its limits: Guard finding IDs and check IDs are run-local, so identity is computed from recorded facts (Policy rule, source, adapter rule, location, package, fingerprint). Code moved within a file is paired by position and labelled; code moved to another file without a declared rename, renamed tool rules and reworded semantic findings may appear as one "not observed" plus one "new", annotated as a possible move when the facts allow. The comparison is a reading aid, never verification evidence.

## User Stories

- **US-01:** As a Developer, I want to compare exactly two Guard reports I name, on my explicit request, so that I see what changed between those runs without the agent reading all history, re-scanning or fixing anything (R-11).
- **US-02:** As a Developer, I want each finding classified new / still present / not observed this time / not comparable, so that I understand the change without a false "fixed" claim (R-12, G-02).
- **US-03:** As a Developer, I want differences in artifact scope, adopted Policies, check coverage, methods and tool or tool-data versions detected before classification, so that a finding is never reported as gone or new merely because the second run looked differently (R-12).
- **US-04:** As a Developer, I want the rule that makes two findings "the same" to be stated, with its limits (moved code, renamed files, reworded semantic findings), so that I can judge each pairing.
- **US-05:** As a Developer, I want edited, inconsistent, unsupported or expired-evidence reports handled honestly, and masked values to stay masked, so that the comparison never overstates what the inputs prove or leaks a secret.

## Acceptance Criteria

Preliminary AC-002G-01 is refined by AC-002G-01a…01i (request and read boundary), 02a…02k (identity) and 03a…03g (classification). Preliminary AC-002G-02 is refined by AC-002G-04a…04m (comparability) and 03f, under the DAO-approved interpretation below. Groups 05 (input integrity and strict validation), 06 (output) and 07 (path safety) cover the edge-case, review and output gates of this refinement.

**DAO-approved interpretation of preliminary AC-002G-02 / R-12 (DAO-010 OQ-03).** R-12 requires comparability to be checked first so that a disappearance is never written as fixed. "Affected findings" in AC-002G-02 are the findings whose class depends on appearing or disappearing between the runs — unpaired findings. They are strictly gated by BR-04/BR-09 and become "not comparable" on any scope, coverage, Policy, method, tool or tool-data difference. A finding observed in both runs under the identity rule is an observation in each run, not an inference from coverage, so it stays "still present"; every Policy, tool and tool-data difference is shown as a note on the pair and the number of still-present pairs with differences is counted. Wording is "observed in both runs under the stated identity rule", never "same issue confirmed". Rationale: this keeps the not-fixed protection on the only findings a coverage difference can mislead, and avoids classifying almost every Trivy pair as not comparable because its databases update daily.

Fixture convention: "result" = the structured result `x-ipe-docs/secure-code/reports/guard/<verification-id>.json` (schema `ai-secure-code-toolkit/guard-result/v1`); "report" = its Markdown twin `<verification-id>.md` with the `guard-result-sha256` footer; E = earlier run, L = later run.

## Functional Requirements

- **FR-002G-1 Compare request.** Input: project root, earlier report and later report (verification ID `gv-…` or exact `<id>.json`/`<id>.md` path directly in the project's `reports/guard/`, DAO-010 OQ-01), `--json`. Process: resolve both names to IDs, refuse identical, open, unknown or out-of-folder reports, refuse reversed, equal or unknown end order (DAO-010 OQ-04). Output: toolkit result envelope with one next step per refusal.
- **FR-002G-2 Load inputs.** Resolve both names to verification IDs first (DAO-010 OQ-01; FR-002G-9 path safety); then read each structured result and Markdown report only; verify schema (`ai-secure-code-toolkit/guard-result/v1` supported) and ID/file-name agreement; apply the strict validation contract (FR-002G-2a); compute each result's SHA-256; run the integrity checks (FR-002G-2b); check run-folder existence only (no content read).
- **FR-002G-2a Strict validation contract (every consumed v1 field, before any pairing or writing).** Types of every consumed object, list and scalar at every nesting level; enums from the delivered value sets as the delivered writers emit them (`verdict`; ledger `STATES` plus `excluded`, which the engine writes for user exclusions; `SEVERITY_VALUES`; Reviewer `FINDING_RESULTS` plus `not_required`, which the engine writes for findings that need no review; target `kind`; `CHANGES`; method `KINDS`; Policy `at_conclusion` `unchanged`/`changed`/`missing`; adapter `method_status`); uniqueness (target paths, adopted rules, check IDs, finding IDs, adapter-run numbers, one ledger entry per planned check); referential integrity finding↔rule↔check↔target, ledger↔check/finding, N/A/exclusion↔adopted rule, risk acceptance↔finding, finding `tool.run`/`tool.adapter`↔`adapter_runs` (`n`, `adapter`) and finding `source`, adapter-run check keys↔planned checks; digest forms (`sha256:` + 64 hex; delivered sentinels only where the engine writes them, e.g. `missing` at conclusion, none for deleted targets); timestamps `YYYY-MM-DDTHH:MM:SSZ` with `ended_at` ≥ `opened_at`; target changes (`renamed` ⇔ `old_path`, unique `old_path`, deleted without content digest at open); merges (`merged_into` and every `merged_from` entry name an existing finding other than the finding itself; no `merged_into` cycle; a `merged_into` target lists the finding in its `merged_from`; acyclic merge chains and re-merge disagreements, which the delivered writer produces, are accepted and resolved per AC-002G-05s); non-negative integer counts and positive lines. Any violation → refusal naming the rule and JSON path, never the value. Exact rule list finalized in technical design against the delivered writers; it must not be looser than this list.
- **FR-002G-2b Integrity checks (per run).** (i) result bytes equal the canonical serialization of the parsed result (delivered `dumps_json`); (ii) footer digest equals the result SHA-256; (iii) the complete Markdown equals the canonical rendering of the parsed result (delivered `report.render`). Any failure or a missing Markdown → run marked "input integrity unresolved" with the failed checks; the structured result is used only if it passed FR-002G-2a; otherwise refuse. Nothing is repaired or written in a compared run.
- **FR-002G-3 Normalise findings.** Exclude findings with `merged_into` set; map E paths through L's declared renames (`change: renamed`, `old_path`); compute identity keys (BR-05…BR-08).
- **FR-002G-4 Pair.** Within each identity group pair by equal valid tool fingerprint, then equal line, then ascending line order (no-line last, then recorded order); label the basis (exact / fingerprint / position / declared rename / semantic weak). Any group with more than one candidate on either side that is not resolved by fingerprint or equal line is paired by position and labelled "position" — never a silent choice (DAO-010 OQ-02).
- **FR-002G-5 Comparability.** For every unpaired finding evaluate against the other run: artifact scope, target stability, location deletion (both directions), Policy adoption/state digest, covering check and its ledger state, N/A and exclusions, method parity, Adapter build/rule-configuration/(Opengrep) include-ignored parity, Trivy component and scanner/mode parity, Adapter coverage gaps (BR-09). Record all failing conditions as reasons with both values.
- **FR-002G-6 Classify.** Pair → still present ("observed in both runs under the stated identity rule"; attribute changes listed; every Policy/tool/tool-data difference listed as a note; pairs with differences counted — DAO-010 OQ-03); unpaired L → new or not comparable; unpaired E → not observed this time or not comparable; add "possible move" and "target content unchanged" annotations.
- **FR-002G-7 Render.** Build one structured comparison (schema `ai-secure-code-toolkit/guard-comparison/v1`, name final in technical design) and render the Markdown from it: input-integrity warnings first (when any), then the not-fixed statement; the structured comparison carries a mandatory top-level `input_integrity` entry per run referenced by every entry derived from an unresolved run; both runs (ID, opened/ended, verdict and reasons, result SHA-256, integrity state, evidence availability, cancellation); comparability summary; class counts and count of still-present pairs with differences; per-class tables; still-present attribute changes and notes; risk acceptances per run; identity rules and limits; provenance and not-evidence statements. Apply masking to every free text written; never write `tool.secret` values.
- **FR-002G-8 Store.** Write both files directly in `x-ipe-docs/secure-code/reports/guard/comparisons/<comparison-id>.{json,md}` (DAO-010 OQ-05); the compare command creates `comparisons/` on first successful write (no init-layout change). Writer (DAO-011 (d)): reuse the delivered `knowledge/durable.py` no-follow folder handles, exclusive-open and fsync primitives read-only (no change to that module); create each final name exclusively without following links and never overwrite (collision → new ID or refusal); refuse when `comparisons/` or any parent is a link; commit order structured comparison → fsync → Markdown (footer = SHA-256 of the structured comparison) → fsync → folder fsync → re-verify the pair before reporting success; on any failure remove the partial files it created. A lone or mismatched pair is never a valid comparison. Comparison ID allocated per comparison; no other writes.
- **FR-002G-9 Path safety.** Accept a verification ID, or a path that after normalization relative to the project root is exactly `x-ipe-docs/secure-code/reports/guard/<id>.json|.md` (no absolute path, no `..`, no subfolder); check every path component from the project root and both twins without following symbolic links; refuse a symlinked `reports/guard/`, input twin or `comparisons/`; create outputs exclusively (no overwrite, no follow) and handle name collisions; re-verify, without following links, that `comparisons/` is still the same folder inside the project after the safety checks, immediately before each final-name link and before reporting success, so that no final-name link is performed after a mismatch is detected; on a mismatch remove, only through the command's held folder handle, every file and temp entry the command created, remove a `comparisons/` folder the command created only while it is still the same entry in `reports/guard/`, and fail, so that after handled failure no command-created file or temp entry remains outside the project; an empty command-created `comparisons/` directory may remain where another process moved it (the same on every platform, including Windows) (v1.2.3, DEC-07 A; directory clause v1.2.4; residual race: Honest Limits).
- **FR-002G-10 Regression oracle (frozen clock, DAO-011 (a); v1.2 re-review nit).** Control and subject projects run under one frozen clock (including the clock behind Guard budget consumption) so all outputs and file effects compare exactly; no field is normalized. An unfrozen fallback is not allowed: delivered `guard conclude` also recalculates and persists consumed budget time (`service.consumed()`, `runs.bump_clock()`), so an unfrozen run would produce false regressions. Any differing byte fails the test.

## Non-Functional Requirements

- **NFR-002G-1 Determinism.** No AI in the script; identical inputs give identical comparison data except ID and creation time.
- **NFR-002G-2 Read boundary and safety.** Reads application-data content only from the two named results and reports; no target, run-folder content, other report, adopted-scope, knowledge or tool read; no execution, no network, no model API.
- **NFR-002G-3 Masking.** Free text is taken from already-masked results and masked again with the FEATURE-001-B pre-check patterns plus Guard additions (FEATURE-002-A NFR-002A-2) before writing; `tool.secret` values are never written or echoed; masking is pattern-based, not a data-loss-prevention guarantee.
- **NFR-002G-4 Consistency and write safety.** Exclusive, no-follow output creation; never overwrite; files and folder fsynced; defined commit order (structured comparison, then Markdown as commit marker) with re-verification before success; partial files removed on failure; no write outside `comparisons/`. Windows: the delivered `durable.py` Windows path fallback (lstat/identity checks, no directory fsync) applies — the no-follow race guarantee and folder fsync are weaker there, stated as a limit, as in FEATURE-001-D.
- **NFR-002G-5 Bounded inputs (v1.2.2; limits and refusal wording v1.2.3; pre-scan, value limit and envelope wording v1.2.4).** No per-result item cap is claimed: the delivered `MAX_ITEMS` (1000) bounds one record request, and results accumulate across records. Each input is read whole, but only within fixed comparison limits: at most 64 MiB per structured result and per Markdown report, JSON nesting depth at most 64, at most 2,000,000 JSON values and at most 1 MiB (UTF-8, decoded) per string in a structured result. Depth, value count and string length are enforced by a streaming pre-scan of the raw bytes before the JSON is parsed. The bounds cover a supported large-run envelope plus ordinary records and all measured delivered test flows; the envelope's finding counts are design capacity targets, not limits enforced by the delivered Adapter writers, so larger valid results — for example one aggregating several large runs, or one run with more findings than the envelope — may exceed the limits and are refused deterministically. The technical design justifies each limit numerically, does not claim which limit binds first except for measured delivered shapes, and tests each limit just below and just above it; the just-below tests measure peak memory against a stated minimum-memory expectation, and the limits are lowered in a later revision if the measured peak is unsuitable. A structured result beyond a limit is refused before any pairing or writing (nothing is written); the refusal names the limit, the rule and a next step and states that the comparison is not possible — it does not declare the run or its result invalid. A result that cannot be canonically serialized for any other reason is refused per AC-002G-05b. A Markdown report beyond the byte limit is not read and its run is marked "input integrity unresolved" per AC-002G-05c. Within the limits, memory use grows with the input (honest limit); no performance threshold is claimed.
- **NFR-002G-6 Portability and independence.** macOS, Linux and Windows path rules; no dependency on X-IPE task or workflow files.

## Business Rules

- **BR-01:** A comparison runs only on an explicit request naming exactly two concluded reports resolved from the supplied project's report store (`reports/guard/` directly, by ID or exact `<id>.json`/`<id>.md`); the agent never selects reports itself and may list file names only (R-11, DAO-010 OQ-01, OQ-06). "Same project" means exactly this resolution; the reports' provenance cannot be proven and copied foreign reports are not detected.
- **BR-02:** Only the two named results and their reports are read as application data (metadata checks and the two output writes aside); never all history, raw evidence, targets or other reports; no scan, re-verification, fix, tool, model or network (R-11).
- **BR-03:** Classes are exactly new, still present, not observed this time, not comparable; "fixed" (or resolved/remediated/improved) is never a class, count or description (R-12).
- **BR-04:** Comparability is checked before classifying an unpaired finding; any difference that could explain its absence or appearance makes it not comparable, with reasons (R-12).
- **BR-05:** Run-local finding IDs, check IDs and titles are never identity.
- **BR-06:** Tool finding identity = adopted Policy rule + Adapter + tool rule ID + path (after declared rename); Trivy vulnerabilities add package name and package path; lines and fingerprints only order pairing (FR-002G-4).
- **BR-07:** Semantic finding identity = adopted Policy rule + source + path (after declared rename) + CWE (or none); always labelled weak; ambiguous groups are paired by position and labelled "position" (DAO-010 OQ-02).
- **BR-08:** Only renames declared in the later run's targets are followed; no content-similarity matching.
- **BR-09:** Comparable against the other run requires all of: path is a target there and stable/complete in both runs; not recorded as deleted in either run (DAO-010 OQ-09, both directions); Policy adopted in both with equal state digest and unchanged at both conclusions; a covering check there with ledger `met` or `not_met`, not excluded, not N/A; a method of the same kind (same Adapter for tool findings, non-Adapter reading/document for semantic findings); for tool findings equal Adapter build, rule configuration digest and (Opengrep) include-ignored, a successful run without skipped/unaccounted items or gaps, and for Trivy equal components and scanners/mode.
- **BR-10:** A pair observed in both runs under the identity rule is still present even when Policy, tool or tool data differ; every difference is a note and such pairs are counted; wording never says "same issue confirmed" (DAO-010 OQ-03, DAO-approved interpretation of AC-002G-02 / R-12).
- **BR-11:** Reviewer classifications, severities and risk acceptances are shown per run; acceptances never carry over (002-A BR-11); no verdict is recomputed or derived.
- **BR-12:** The comparison is not verification evidence (each output says so) and does not extend evidence retention; comparison files stay until the user removes them and are excluded from evidence cleanup (002-A BR-12, DAO-010 OQ-05).
- **BR-13:** Masked values stay masked; `tool.secret` values (at any nesting level) are never output, in results, Markdown, refusals, reasons or notes.
- **BR-14:** Inputs are trusted only after strict validation (FR-002G-2a); any integrity inconsistency is stated first, the structured result wins only after it passed strict validation, and nothing is repaired or written in a compared run (DAO-010 OQ-08, review finding 2).
- **BR-15:** Path safety: inputs only as exact twins directly in `reports/guard/`, resolved to the ID before any read; no `..`, absolute paths, subfolders or symbolic links anywhere on the path; outputs only in `comparisons/`, created exclusively without following links; nothing written outside the project.
- **BR-16:** Stop rule: no change to 002-A…D files, schemas, reports, folders or existing instructions beyond the cited plug-in points; anything else is a human CR (DAO-010).

### Honest Limits

- Identity is computed from recorded facts, not proven sameness: moved code across files without a declared rename, renamed tool rules, changed CWE or source names of semantic findings, and same-key collisions can mispair or split findings; labels ("position", "semantic identity (weak)", "possible move (unverified)") show where.
- "Still present" means observed in both runs under the stated identity rule, not the same issue confirmed.
- Project provenance of the two reports cannot be proven; a consistently edited result + Markdown pair cannot be detected; a report rendered by an older renderer is indistinguishable from an edited one ("input integrity unresolved").
- Trivy per-path accounting is private and not read; any skipped/unaccounted count makes absences of that check not comparable.
- Semantic review is not deterministic; a "not observed this time" semantic finding may only mean it was not reported again.
- A concurrent process of the same user that moves `comparisons/` (or a parent) outside the project in the instant between the command's folder-identity check and its next file operation cannot be prevented portably; the file it then writes may exist outside the project until the command removes it through its held folder handle (a move out and back is not detected). After handled failure no command-created file or temp entry remains outside the project, but an empty `comparisons/` directory the command created may remain where the other process moved it: the command never removes a folder by path outside `reports/guard/` (the same on every platform, including Windows). Only the masked comparison is exposed; no privilege boundary is crossed (v1.2.3, DEC-07 A; directory clause v1.2.4).
- A very large legitimate result — for example one aggregating several large Adapter runs, or one run with more findings than the supported large-run envelope (whose figures are design capacity targets the delivered Adapter writers do not enforce) — can exceed the NFR-002G-5 comparison limits; it is refused and cannot be compared, although the run and its result remain valid (v1.2.3; envelope wording v1.2.4).

## Out of Scope

- Comparing more than two reports, trends over history, dashboards, scores or percentages.
- Comparing Copilot reports (FEATURE-003-A) or mixing Copilot and Guard reports.
- Starting scans, re-verifications or fixes from a comparison; reusing earlier evidence (V-18).
- Content-similarity or AI matching of findings; reading raw evidence or target files.
- Changing 002-A…D schemas, reports, ledger or verdict rules; adding a project identity to results (would be a CR).
- Deleting comparison files (user removes them manually).
- Recording a renderer/toolkit version in Guard results (optional human CR candidate on FEATURE-002-A, DAO-011 (c)); a viewer or `show` command for comparisons.

## Technical Considerations

- Command name/options, comparison ID format, structured comparison schema name and reason codes are decided in technical design.
- Reuse 002-A read helpers, the canonical serializer (`dumps_json`), the canonical renderer (`report.render`) and masking in-process, read-only; do not reuse `guard show`'s current-target digest check (it reads targets) or `_repair_report` (it writes to the run).
- The delivered `runs.read_result` only checks schema and ID; the strict validator (FR-002G-2a) and the exclusive no-follow writer live in the new comparison module, not in 001-A/002-A code.
- Path checks must be applied component-wise without following links (e.g. `lstat`/no-follow opens relative to an opened directory) so a substitution between check and use cannot redirect reads or writes; exact mechanism per platform in technical design.
- Delivered timestamps have one-second resolution, so equal end times are possible and are refused (01g).
- `durable.write` replaces existing files, so it is not used for final names; exclusive final creation uses the same no-follow folder handles and exclusive-open/fsync primitives (`Tree`, `entry`, exclusive no-follow open, folder fsync) without modifying `durable.py`; where a primitive is private, the new module repeats its flags rather than changing the delivered module (technical design decides).
- Regression tests freeze the clock at test level (clock substitution in the test process) without changing delivered code.
- Opengrep fingerprints may be absent or placeholders; only valid hex fingerprints (as recorded) take part in pairing.
- Trivy component details and per-check counts are taken from `adapter_runs` in the result; per-path Trivy accounting lives in the private manifest and is not read, so any skipped/unaccounted count for the check makes absences not comparable (conservative).
- Older v1 results may predate 002-B/C/D sections; treat absence as not recorded.
