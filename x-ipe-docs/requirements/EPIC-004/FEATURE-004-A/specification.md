## Overview

FEATURE-004-A keeps the toolkit's learning **small, useful and expiring**. After real Guard verifications and Copilot collaborations, the agent (on behalf of the run) or a person can propose an **improvement suggestion**: a concrete, structured proposal to improve one formal toolkit asset of the project — a Local knowledge rule, a Preset or tag, a Guard/Copilot/Framework skill text, an Adapter mapping — or to report a scanner-tool defect. A proposal states the observed and the expected behaviour, the exact place in the target (locus), one proposed operation, its value and one or more verification assertions, and cites resolvable evidence (a finding, check or suggestion in a concluded Guard or Copilot report, or a located project file range).

The deterministic `secure-code` script checks everything that can be checked mechanically (completeness, resolvable evidence and target, locus, closed categories and operations, attribution, duplicate fingerprint, cap). Whether a suggestion is truly valuable is a **Maintainer judgement**, never claimed by the script. At most **10** suggestions are active; a full queue never silently replaces anything and never keeps an unbounded waiting list: the only waiting place is a small "awaiting Maintainer choice" hold of at most **3** user suggestions outside the cap.

An agent's suggestion expires **30 days** after first queueing while pending; reading or re-proposing never renews it. An approved suggestion that is not applied expires **30 days after approval** (DAO-015 interpretation). An **unreviewed user suggestion never expires**: 30 days after it was first stored it is marked "review overdue" and keeps its cap slot until a Maintainer reviews it (human decision B15 part 1). Intake order is validate → deduplicate → cap. A valid, non-duplicate user suggestion arriving when 10 are active is **held** — never auto-expired, auto-removed or auto-promoted, decided only by a Maintainer; when the hold is full too, it is refused at intake with nothing stored, and the user keeps the text and is told the active list and next steps (human decision B15 part 2). An agent proposal at a full queue is refused explicitly with nothing stored and is never held. An **evidenced severe security issue** — a Reviewer-confirmed Guard finding with final severity High or Critical that relates to the suggestion's target, plus an explicit Maintainer exemption — does not expire under the ordinary TTL while its evidence stays unchanged. Terminal suggestions are removed by an explicit, idempotent cleanup **30 days** after they became terminal; formal knowledge and changelogs are never deleted.

A suggestion is always a **candidate**. Only a verified Maintainer approves, rejects, exempts or marks it applied. **Applied** requires that the target changed since approval at the proposed locus and that every verification assertion of the proposal is covered by verification evidence bound to the changed target. Expiry is evaluated lazily from recorded times; no command rewrites a record to expire it. Every record carries an integrity code under a project-private key, created only by this feature's writing commands, so that ordinary edits are detected and quarantined; only a Maintainer can recover a quarantined record. All text from findings, reports, files and users is untrusted data, stored masked and rendered as neutralized Markdown. This feature never changes a formal asset, never applies anything automatically and adds no model call, network access, key service or third-party package. Autonomous optimization from Lessons is FEATURE-004-B (out of scope, parked).

**Two different "suggestions".** A *Copilot suggestion* (FEATURE-003-A) is advice about a business artifact inside one collaboration. An *improvement suggestion* (this feature) is a proposal about the toolkit's own formal assets. A Copilot result is one evidence source here; Copilot suggestions are never moved into the improvement queue as such. The X-IPE workflow's own lesson-learned skill is unrelated to this product feature.

**Lesson (DAO-015 OQ-06 A).** A Lesson is an approved improvement suggestion record; there is no separate Lesson store or permanent memory. FEATURE-004-B may refine this by CR.

**Definitions.**
- *Submitted user suggestion*: a `propose` with source `user` that passes the mechanical completeness checks (AC-004A-01l). Input that fails them is returned to the user as "not submitted" with every missing item. A mechanically complete user suggestion that is held or refused at a full queue is still a submitted user suggestion to which L-10 applies; its handling is the human decision B15 part 2 (held → decided only by a Maintainer; hold full → refused at intake, user informed, nothing stored) and the term is not narrowed to avoid L-10.
- *Review*: a verified Maintainer's `approve` or `reject` decision with a reason. Expiry, listing, duplicate folding and toolkit refusals are not review.
- *Effective state*: the state computed at command time from the recorded state, recorded times, exemption evidence and the clock (BR-09); it is never written back.
- *Target state*: typed as `present` (with digest), `inactive` (with digest; `knowledge_rule` deactivated per FEATURE-001-D) or `absent` (the target ID no longer resolves). `absent` is a sentinel, never a digest value.
- *Held*: a submitted user suggestion that arrived when 10 were active, kept outside the cap in "awaiting Maintainer choice", at most H = 3 at a time (human decision B15 part 2). It is neither active nor terminal, never expires and leaves the hold only by a verified Maintainer's `admit` or `reject` (AC-004A-03h, 03l).
- *Review-overdue time*: for an unreviewed `user` suggestion, 30 days after it was first stored — its hold time if it was held, otherwise T0. From then on it is labelled "review overdue" (display and ordering only; no state, cap or hold change; human decision B15 part 1).

Fixture convention: "Guard result" = `x-ipe-docs/secure-code/reports/guard/<verification-id>.json` (schema `ai-secure-code-toolkit/guard-result/v1`; adopted Policies in `scope.adopted[*]` with `rule`, `state_digest`; Adapter runs in `adapter_runs[*]` with `adapter`, `version`, `binary_digest`; findings with `id`, `rule`, `final_severity`, `review`); "Copilot result" = `x-ipe-docs/secure-code/reports/copilot/<collaboration-id>-r<n>.json` (schema `ai-secure-code-toolkit/copilot-result/v1`); "suggestion file" = `x-ipe-docs/secure-code/improvements/<suggestion-id>.md`; "private folder" = `.x-ipe/private/secure-code/improvements/`; "Maintainer" = the role verified by the delivered `auth` check used for knowledge and tag writes; T0 = first-queued time; A = approval time.

## User Stories

- **US-01:** As a Maintainer, I want only complete, evidenced, specific and verifiable suggestions to be queued, with the value judgement left to me, so that I review a few useful items instead of a backlog of generic ideas (L-01, L-02).
- **US-02:** As a Maintainer, I want duplicates of the same problem folded into the existing item without losing the new text, and the active queue capped at 10 without silent replacement, so that the queue stays small and I decide what is dropped (L-02, L-03, L-04).
- **US-03:** As a Maintainer, I want stale suggestions to expire and terminal ones to be cleaned 30 days later, while an evidenced severe security issue does not expire under the ordinary TTL, so that stale ideas disappear but serious problems are not lost (L-05, L-06, L-07).
- **US-04:** As a User, I want my submitted suggestion to be reviewed by the Maintainer and never silently executed or dropped, so that my input is taken seriously (L-10).
- **US-05:** As a Maintainer, I want a suggestion to count as applied only after the proposed change actually happened at the proposed place and its verification assertions are covered, so that "approved" is never mistaken for "done" (L-13).
- **US-06:** As a Developer using Guard or Copilot, I want the agent to propose improvements only from concrete run evidence, to tell me about refusals and never to obey instructions found in evidence, so that runs produce honest feedback without noise or manipulation (L-10, L-11, L-12).
- **US-07:** As a Maintainer, I want each suggestion stored as one readable, safely rendered, integrity-protected Markdown file with masked sensitive values and no second source of truth, so that I can read and trust it (L-08, L-09).

Overdue user suggestions keep cap slots, so full-queue holds and refusals may be more frequent until a Maintainer reviews (DAO-016 note). Agent suggestions follow L-05.

**Human decision B15 part 2 (OQ-15, 2026-10-24): (iii).** A mechanically complete, non-duplicate **user** suggestion arriving when 10 suggestions are active is stored as `held` in the "awaiting Maintainer choice" hold outside the cap, capacity H = 3. A held suggestion is never auto-expired, auto-removed or auto-promoted and is decided only by a verified Maintainer: *review now* — `review --decision reject --reason` (this is also the *decline with a recorded reason* choice), or `review --decision admit` while fewer than 10 are active, followed by the normal review; *free a slot* — a separate `review --decision reject` (or `apply`) of a named active suggestion, then `admit` (AC-004A-03h, 03l). When 3 are held, a further such user suggestion is refused at intake: nothing is stored; the user keeps the text and is told the active list, the hold and the next steps. Agent proposals at a full queue: explicit refusal, nothing stored, never held (DAO-016).

Command order (BR-15), used by every "nothing is written" assertion: parse and validate input and authority without writing → acquire the queue lock → re-read and revalidate → perform the one authorized operation → commit atomically. No command writes anything to record expiry.

## Functional Requirements

- **FR-004A-1 Propose.** Input: project; proposal file (source `user`|`agent`; target kind and ID; locus; category; operation; goal; observed and expected behaviour; value/impact; proposed change; verification assertions; evidence references; optional severity note, stored as a claim only). Order per BR-15: mechanical checks (AC-004A-01a…01g, 01i, 01j) without writing; lock; revalidate; duplicate/re-proposal handling (FR-004A-2); judgement flags (user) or refusals (agent) per BR-03a; cap (FR-004A-3); allocate ID; mask and neutralize; write one file with integrity code. Output: suggestion ID and path, fold result, or refusal with every reason and next step.
- **FR-004A-2 Duplicates and re-proposals.** Fingerprint per BR-06; folding of new evidence and differing text without renewal; secondary "possible duplicate" flags; terminal-retention re-proposal rules (AC-004A-02).
- **FR-004A-3 Cap and full queue.** Active per AC-004A-03a; max 10; intake order validate → deduplicate → cap; agent at cap: explicit refusal, nothing stored; user at cap: stored as `held` in the "awaiting Maintainer choice" hold (capacity 3, outside the cap), hold full → intake refusal with nothing stored (AC-004A-03g, 03h, 03l); never replacement, automatic promotion or unbounded waiting list.
- **FR-004A-4 Review (Maintainer).** `approve` / `reject` with mandatory reason, and `admit` / `reject` for held items (admit only while fewer than 10 are active); approval records A, deadline, target state/digest and private target snapshot.
- **FR-004A-5 Exemption (Maintainer).** Grant (bound to suggestion, finding, result SHA-256, relationship, reason) or revoke; lapses fail-closed (BR-07).
- **FR-004A-6 Effective state.** Pure function of record, exemption evidence and clock; never written back; unreviewed `user` suggestions (pending or held) never expire and carry "review overdue" from their review-overdue time (B15 part 1).
- **FR-004A-7 Apply (Maintainer).** Change evidence bound to the locus, verification records bound to the current target digest and covering all assertions, Maintainer statement, re-read before commit.
- **FR-004A-8 List / Show.** Read-only views with effective state, flags (including "review overdue"), active count, the held section "awaiting Maintainer choice" with its count, value label and evidence resolution; `--json` in the delivered result envelope.
- **FR-004A-9 Cleanup.** Explicit, any role, deterministic, idempotent; removes only terminal records (recorded or effective) past 30-day retention and their private data; lists removed, retained, quarantined and unrecognized entries.
- **FR-004A-10 Skill guidance.** Self-contained additive sections in the Guard, Copilot and Framework skills plus new skill-text tests (AC-004A-10a…10d, 10i).
- **FR-004A-11 Recover (Maintainer).** `recover --id --decision reseal|reject --reason` for quarantined records (reseal = full revalidation, re-masking and body regeneration before the new integrity code; any failure → reject only; reseal of a `held` record refused while 3 valid held suggestions exist; reseal of a record that would be effectively active refused while 10 valid active suggestions exist; reseal duplicating a valid active or held fingerprint refused; every reseal refused while the cap is exceeded) and `recover --new-key --reason` for a lost key; never automatic (AC-004A-03m, 08l, 08o…08s).

## Non-Functional Requirements

- **NFR-004A-1 Safety.** No network, no model, no Adapter/tool/Reviewer start, no execution of project content; masking with the delivered FEATURE-002-A patterns (same honest limit as NFR-002A-2); all external text is untrusted data, neutralized when rendered.
- **NFR-004A-2 Determinism.** Same files, key and clock → same results; frozen clock injectable for tests.
- **NFR-004A-3 Bounded work.** Active items ≤ 10; terminal files exist only through Maintainer decisions or expiry and leave after 30 days; a directory-entry budget, input size limits and an evidence/assertion count limit (values fixed in the technical design) bound every command with refusal above them (AC-004A-08m, 08j); evidence resolution reads only cited result files and cited file ranges.
- **NFR-004A-4 Durability and integrity.** Atomic replace with fsync for every write; one lock for all writers; HMAC-SHA256 integrity code per record under a 32-byte project-private key with owner-only permissions; no partial files after failure.
- **NFR-004A-5 Portability.** Same behaviour on macOS and Linux; Windows follows the delivered lock/durability limits stated for FEATURE-001 primitives.
- **NFR-004A-6 Readability.** Suggestion files are readable Markdown without the toolkit; command results follow the delivered text/`--json` conventions.

## UI/UX Requirements

No graphical UI. Command-line output follows the delivered conventions: a short human-readable summary, every refusal with reason and next step ("not submitted", "not queued", "duplicate", "changed during apply"), `--json` for the structured result. Suggestion files are plain, neutralized Markdown. List output always shows "n / 10" and the held section "awaiting Maintainer choice n / 3", labels `approved` as "approved — not applied" and every value as "not machine-verified".

## Business Rules

- **BR-01 Candidate ≠ applied.** No state other than `applied` may be described as applied, implemented or fixed (L-13).
- **BR-02 No self-execution.** This feature never changes a target or any formal asset; changes are made by the Maintainer through existing commands or by FEATURE-004-B under its own policy (L-12).
- **BR-03 Mechanical admission (both sources)** requires: one resolvable target; resolvable locus; closed category and operation; observed/expected behaviour, value, proposed change and ≥ 1 verification assertion; ≥ 1 resolvable evidence reference identifying a specific item; for `agent` ≥ 1 Guard or Copilot result item (L-01, L-10). Failure = "not submitted".
- **BR-03a Judgement checks** (attribution mismatch, possible duplicate, doubtful value): refuse `agent` proposals for attribution mismatch; for `user` proposals only flag them for the Maintainer (L-10). Value is never machine-judged.
- **BR-04 Closed categories:** `false_positive_pattern`, `missed_detection`, `unclear_guidance`, `missing_example`, `wrong_mapping`, `tool_defect`, `remove_or_retire` (L-02).
- **BR-04a Closed operations:** `add_example`, `add_negative_example`, `change_text`, `change_detection`, `change_mapping`, `retire`, `report_tool_defect`.
- **BR-05 Attribution table:** `tool_defect` → `tool` or `adapter`; `false_positive_pattern`/`missed_detection` → `knowledge_rule`, `adapter`; `unclear_guidance`/`missing_example` → `knowledge_rule`, `skill`, `preset`, `tag`; `wrong_mapping` → `adapter`, `preset`, `tag`; `remove_or_retire` → any kind.
- **BR-06 Problem fingerprint:** SHA-256 over (target kind, target ID, normalized locus, operation). Same fingerprint among active or `held` items = duplicate → fold into that record (no renewal, no new hold entry, no text loss). Equal normalized change text or the same evidence item on the same target with another fingerprint = "possible duplicate" flag only (DAO-015 OQ-11).
- **BR-07 Evidenced severe security issue:** bound to one suggestion: a finding in the suggestion's recorded evidence, in a concluded Guard result with `review` = `confirmed` and `final_severity` High or Critical, related to the target (`rule_of_finding`, `adapter_of_finding` or `maintainer_stated`), plus an explicit Maintainer exemption with reason, granted only while effectively active. It lapses fail-closed when the result is missing, its SHA-256 changes or the finding no longer qualifies. Never automatic; AI self-report, original/default severity and Copilot severity never suffice (L-06, DAO-015 OQ-10).
- **BR-08 Active** per AC-004A-03a; cap 10; never filled or replaced, and never wait-listed except the "awaiting Maintainer choice" hold of fixed capacity 3 outside the cap for user suggestions (BR-17; human decision B15 part 2) (L-03, L-04). Reseal never pushes the valid active count past 10 or creates a duplicate (AC-004A-08s); if more than 10 valid active suggestions are found (restored older files), commands report "cap exceeded" and refuse new admissions and reseals until a Maintainer brings the count to 10 or below, deleting nothing automatically (AC-004A-03m, DAO-023).
- **BR-09 Deadlines (effective, lazy):** agent `pending_review` → T0 + 30 d; user `pending_review` and `held` → no expiry; labelled "review overdue" from the review-overdue time = (hold time if it was held, else T0) + 30 d, which admission does not renew (human decision B15 part 1); `approved` → A + 30 d (DAO-015 interpretation); effective exemption suspends these; reading, folding and re-proposing never renew (L-05).
- **BR-10 Terminal retention:** `rejected`, `expired`, `applied` records (recorded or effective) are removed by explicit cleanup at `terminal_at` + 30 d; formal knowledge, changelogs and reports are never deleted (L-07, DAO-015 OQ-08).
- **BR-11 Authority:** approve, reject, admit, exempt, revoke, apply and recover require the verified Maintainer; propose, list, show and cleanup are open to the User and the agent (DAO-015 OQ-01, OQ-08; DAO-016).
- **BR-12 Agent triggers (closed list, after a concluded run only):** a finding classified `false_positive` by a valid review; a confirmed finding a Local rule missed or mis-described; a check `unconfirmed` because no method/Adapter could cover it; a recorded severity conflict; an Adapter/tool error or wrong mapping; a Copilot suggestion `not_applicable` or `policy_changed` traced to rule guidance. Per-run strategy tweaks are never persisted (L-11, DAO-015 OQ-12).
- **BR-13 Single truth with integrity:** the suggestion file is the only authority; its integrity code must verify under the current key; the key is created only by this feature's writing commands (first `propose`, or explicit Maintainer `recover --new-key`), never by read-only commands or `init`; the private folder holds only the key and approval snapshots (L-09, DAO-016).
- **BR-14 Masking and neutralization** before storage and output, including on reseal (re-mask all free text and regenerate the body from the sanitized frontmatter, AC-004A-08o); external text is never instructions.
- **BR-15 Command order:** validate input and authority → lock → revalidate → one authorized operation → atomic commit; no expiry writes.
- **BR-16 Apply binding:** target changed at the locus since approval and every assertion covered by verification bound to the current typed target state, plus Maintainer statement; `retire` per AC-004A-07l (L-13, DAO-015 OQ-14).
- **BR-17 Full queue:** dedupe (against active and held records) before cap; agent proposals refused explicitly with nothing stored, never held (DAO-016); valid non-duplicate user proposals are stored as `held` in the "awaiting Maintainer choice" hold of capacity 3 outside the cap — never auto-expired, auto-removed or auto-promoted, no slot reserved; decided only by a verified Maintainer through one-file commands (`admit` while fewer than 10 are active, or `reject` with a recorded reason; freeing a slot is a separate decision on an active item); hold full (occupancy of 3, counting quarantined held and unparseable files fail-closed, AC-004A-03a) → refused at intake, nothing stored, user told the active list, the hold and the next steps; never more than 3 valid held suggestions (L-04, L-10; human decision B15 part 2, 2026-10-24).

## Edge Cases & Constraints

- Queue full with only exempt or overdue items: every new agent proposal is "not queued"; user proposals go to the hold until 3 are held and are then refused at intake, until a Maintainer applies, rejects, revokes or decides held items (AC-004A-03b, 03g, 04k, 06j).
- A slot frees while suggestions are held: nothing is promoted automatically; a later proposal may take the slot before a held item is admitted, and the Maintainer's `admit` then gets "active queue full" with the item still held (AC-004A-03l).
- A held suggestion past hold time + 30 d is labelled "review overdue" in the hold section; admitting it keeps that overdue time (AC-004A-06j, BR-09).
- A held record that fails its integrity check is quarantined like any other record; if its frontmatter parses with state `held` it counts toward the hold occupancy, otherwise as active, and an unparseable file counts toward both the active count and the hold (fail-closed); it is recovered only by the Maintainer, and reseal of a held record is refused while 3 valid held suggestions exist, so at most 3 valid held suggestions ever exist (AC-004A-03a, 08f, 08o, 08p, 08q).
- Evidence report removed by the user after admission: suggestion stays; `show` flags the reference `missing`; a bound exemption lapses (AC-004A-04j).
- Guard result re-rendered by a risk acceptance: its SHA-256 changes, so a bound exemption lapses; the Maintainer may re-grant with the current result while the suggestion is active.
- Target renamed or deleted after admission (knowledge exit, FEATURE-001-D): `show` flags `target missing`; apply only via `retire` or reject.
- Locus edited away before approval: approval still records the current target; apply checks intersection with the recorded locus in the approval snapshot.
- Same evidence cited by suggestions with different fingerprints: allowed, flagged as possible duplicate.
- Proposal at the moment another item expires: effective state is evaluated at command time under the lock (AC-004A-03d).
- Clock moved backwards: writes refused (AC-004A-09e); clock moved forwards by mistake: items may appear expired early — no write happens, so correcting the clock restores them (lazy evaluation).
- Hand edits of suggestion files or copying a file from another project: integrity fails → quarantine; Maintainer reseal or reject (AC-004A-08f, 08o, 08p).
- Restored older suggestion files (version control, backup): they verify under the same key; more than 10 valid active → "cap exceeded", new admissions and reseals refused until a Maintainer reduces the count; nothing deleted automatically (AC-004A-03m).
- Integrity key deleted: read-only commands report "integrity unverifiable" and create nothing; writes are refused until the Maintainer runs `recover --new-key` and recovers each record (AC-004A-08l, 08n, 08q).
- Retired target reappears (restored file, reactivated rule) before or during `apply`: refused (AC-004A-07l, 07m F2/F3); after `applied`, a reappearance does not change the terminal record.
- Project initialized before this feature: `improvements/` exists from `init`; if absent it is created by `propose` only.
- Many terminal files from repeated reject/re-propose churn: bounded by Maintainer decisions and 30-day retention, plus the directory budget (AC-004A-08m).

### Honest Limits

- The script checks completeness, resolvability, locus, closed sets, attribution, fingerprints and bindings; whether a suggestion has real value is the Maintainer's judgement.
- Source `user`/`agent` is declared by the caller, not authenticated; the delivered toolkit has no multi-user identity (U-01).
- The Maintainer check is qualification only; when the authorization is unlocked an agent could run decisions — guarded by skill text, not by the script (AC-004A-06i).
- The integrity code detects edits and records not written by the toolkit; it is not proof of Maintainer identity, and anyone with project write access who can read the project-private key can forge valid records (same limit as FEATURE-002-F). A reseal trusts the Maintainer's inspection of the quarantined content.
- Genuine older files written by the toolkit under the current key (e.g. restored by a version-control checkout or a backup) verify again: a restored terminal or replaced record reappears as it was, and restored active or held records can exceed the cap or the hold ("cap exceeded" is then reported and new admissions and reseals are refused, AC-004A-03m); the integrity code cannot detect such rollback.
- The integrity key is per checkout (project-private, never committed): another clone of the same repository sees the shared suggestion files as "integrity unverifiable" (no key) or quarantined (its own key) until a Maintainer there reseals or rejects them; a shared key would be a human CR candidate (DAO-023).
- `applied` proves that the target changed at the proposed place after approval and that verification records bound to the changed target cover every assertion; it does not prove that a `test`/`inspection` record's procedure actually ran or that the change achieved its value.
- Expiry is evaluated when a command runs; cleanup removes files only when it is run; there is no background process.
- The toolkit cannot make a Maintainer review: "review overdue" labels and the hold only make waiting visible; while a Maintainer is absent, once 10 are active and 3 are held, further user suggestions are refused at intake (nothing stored, user informed).
- Time depends on the system clock.
- Masking is pattern-based (same limit as NFR-002A-2); neutralization prevents Markdown/HTML structure, not misleading prose.
- Stakeholder outcome (a small, useful queue in real use) is not measured by this feature.

## Out of Scope

- Autonomous optimization, automatic application of Lessons, signed autonomy policy (FEATURE-004-B, parked).
- Changing any formal asset (knowledge, Presets, tags, skills, Adapters, tools) from this feature.
- Automatic mining of reports into suggestions by the script; any model-based similarity or value scoring.
- A separate permanent Lesson/memory store or migration of historical experience (L-15, DAO-015 OQ-06).
- Priority ranking, deferral states, multi-user permissions (U-06) (DAO-015 OQ-02, OQ-04).
- Changes to `status`, routing definition, carriers, Guard/Copilot result formats or `init` layout (DAO-015 OQ-09).
- Maintainer-signed suggestion transitions (would change `auth`): optional human CR candidate (DAO-016).
- The X-IPE workflow's own lesson-learned skill.

## Technical Considerations

- Reuse delivered primitives (root validation, no-follow directory walk, atomic write, private-file creation, exclusive lock, masking, report text neutralization, result envelope, Maintainer check) read-only; do not change them.
- Frontmatter format, canonical form for the integrity code, ID pattern, size/count/directory budgets and snapshot format are design decisions; standard library only (no new package).
- Strict validation of only the Guard/Copilot result fields consumed, as in FEATURE-002-G.
- Locus kinds per target type (Markdown heading path, JSON pointer, line range) and the diff/intersection rule are design decisions within AC-004A-07a.
- Injectable clock for all time decisions; effective state as a pure function.
- Keep the feature's modules separate from `guard/` and `copilot/` so the plug-in surface stays the CLI registration and skill text.
